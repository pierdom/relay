# relay — Claude Code guide

Personal knowledge base: plain-Markdown, **Obsidian-compatible vault** with an AI-integration layer. AI agents publish/query/subscribe over MCP, REST, and SSE; humans edit the *same* files in Obsidian/nvim or the browser/TUI. Posts are tagged, filed into first-level folders, and cross-linked (`[[wikilinks]]`/`#id`).

**Storage** (`RELAY_VAULT_PATH`): one `.md` file per post — the title *is* the filename, metadata in YAML front-matter (`id`, `tags`, `source`, timestamps, `expires_at`, `updated_by`; **no `title`** field). Files are canonical; a disposable **SQLite index** at `<vault>/.relay/index.db` is rebuilt at startup. `id` is authoritative and survives renames. **Ids are monotonic and never reused** — a high-water mark in `<vault>/.relay/last_id` prevents a deleted id from being handed to a new post and silently repointing `#id` cross-links. **Any other front-matter key round-trips verbatim** (`frontmatter.parse`/`serialize`, relay #198 N-2) — Obsidian Properties (`aliases`, `cssclasses`, …) or a hand-added custom field survive every relay-initiated write instead of being silently dropped; relay's own seven keys always win on a name collision. Exposed read-only as `properties` on `PostResponse`/`PostSummary`/`PostRevisionContent` — there is no write API for them, edit in Obsidian or by hand. `updated_by` (relay #198, B-7) is the identity that made the post's most recent write — see "Per-agent identity" under Authentication.

**Folders** (`relay/folders.py`): one folder per domain (`Homelab/`, `Finance/`, … + `Meta/`, `Digests/`, `Inbox/`). Placement is derived from the **first domain tag** at creation. A tag-less note in `Inbox` is moved to a domain folder when it gains its first tag; real folders are human-owned and never auto-moved. Scans are recursive; nesting is one level.

## Running

```bash
cp .env.example .env
uv run uvicorn relay.main:app --reload      # http://localhost:8000, docs at /docs
docker compose up -d                        # or Docker
docker compose pull && docker compose up -d # update

uv run pytest -q                            # tests (tests/ui are browser smokes; they skip without Chromium)
uv run ruff check .                         # lint (config in pyproject.toml)
uvx mypy relay --ignore-missing-imports     # types: clean apart from PyYAML's missing stubs (no mypy dependency added)
uv run playwright install chromium          # once, for browser smokes
RELAY_EVAL_URL=... RELAY_EVAL_KEY=... uv run pytest -m eval -s  # search-quality recall/MRR baseline (tests/eval), skipped otherwise
```

Uses `uv` — never `pip`. Add deps with `uv add <package>` — never hand-edit `pyproject.toml`'s `dependencies` and skip `uv lock`. This caused a real production outage (v1.1.0 → v1.1.1): `sqlite-vec`/`fastembed` were added to `pyproject.toml` without a matching `uv lock`, and the Dockerfile installs via `uv sync --frozen`, which trusts the lockfile literally rather than re-resolving — so every image built from it installed a lockfile that never had those packages, and `relay/vectors.py`'s unconditional `import sqlite_vec` crashed the app on boot. `uv run` silently self-heals a stale lock locally; don't mistake that diff for noise and discard it — recognize it as the lockfile catching up to something pyproject.toml already promised, and commit it.

**Tests always run against a throwaway vault.** `tests/conftest.py` has an autouse `isolated_vault` fixture that repoints `settings.vault_path` under `tmp_path`. Never patch `vault_path` outside `tmp_path` — the real `.env` points at a live Obsidian vault and `rebuild_index` stamps ids into every id-less file it finds there. Put throwaway scripts in `tests/`. **Exception:** `tests/eval` reads real vault content — read-only, over REST, via `scripts/export_vault.py` into a snapshot under `tmp_path` — because the golden query set's expected ids are real posts; it never touches `vault_path` directly and is gated behind `RELAY_EVAL_URL`/`RELAY_EVAL_KEY` so it can't fire by accident. **`tests/eval/golden.yaml` is gitignored, not committed** — real recall queries and real post ids are personal, and this repo is public; copy `golden.example.yaml` to get started, same as `.env.example` → `.env`.

**CI** runs `ruff check` + `pytest` on every push/PR. Ruff: `E,F,I,UP,B,C4,SIM` at line-length 120. `docker.yml` publishes the image on pushes to `main`.

## Attachments

Non-`.md` files live in `<Folder>/assets/`, embedded as `![[file.png]]`. Names are vault-globally unique. **Serving is an inline allowlist by resolved MIME** (`routes/attachments._renders_inline`: raster images, audio/video, PDF, plain text); everything else — HTML, XHTML, SVG-as-document, XML/XSLT, and unknown types — gets `Content-Disposition: attachment` so an upload can never run script in the UI's origin. Never go back to a suffix list: `mimetypes` maps `.xht`/`.svgz`/`.shtml`/`.xsl` to active types too. A caller-supplied `folder` must pass `folders.is_valid_name` (one segment, not `..`, not dot-prefixed) — `Path(folder).name` alone let `..` through. Three byte transports (enforced exactly-one): `data` (base64), `source_url` (server fetches, SSRF-guarded), `upload_id` (presigned slot). Slots are in-memory + disk-staged under `.relay/uploads/`, single-use, TTL'd — **single-worker assumption**. `ATTACHMENT_MAX_MB` (25) → 413. Deleting a post removes only the attachments it embedded that no other post references.

## History

Every write commits the vault to `<vault>/.relay/history.git` (detached git-dir, vault as work-tree — no `.git` in the root, so Syncthing doesn't corrupt it). **Durable**: never wipe `history.git` (same standing as `<vault>/.relay/mcp_oauth/`, the MCP OAuth client storage). The index is disposable; history is not.

**`core.quotePath=false` is pinned on every git call.** Without it, non-ASCII filenames are octal-escaped and the module can't find the file's history. Test fixtures must include non-ASCII titles.

Coverage: every write path + TTL expiry + external edits (watcher commits each debounced batch). Recovery: `GET /posts/{id}/history` + `POST /posts/{id}/restore` — both work for deleted posts; restore keeps the original id. The restorable sha is `log -1 <delete>^ -- <path>` (the last commit that *touched* the file, not the delete commit itself).

Manual recovery: `cd /vault && export GIT_DIR=.relay/history.git GIT_WORK_TREE=.` then plain git. Full runbook: [docs/recovery.md](docs/recovery.md).

## Vault changelog & SSE reconnect (relay #198, N-4)

`relay/changes.py`'s `changes` table is a **materialized index over
`history.git`, not a second source of truth** — same disposable/re-derivable
footing as `posts` (which is why it lives in `index.db` despite recording
things `posts` itself can't, like a delete). `sync()` (startup) and
`record_latest()` (after every existing `history.commit(...)` call) are both
just `_catch_up`: ingest every commit in `{last recorded sha}..HEAD`, or the
whole history if the table is empty. Powers `GET /changes`/`list_changes`
and, via `seq` as the new `Last-Event-ID`, finally fixes audit **B-10/G-07**:
the old cursor was a post id, which has no way to represent "an existing
post changed", so SSE reconnect only ever replayed brand-new posts.

- **`_catch_up` uses a *range*, not "just the latest commit" — this is load-bearing, not a style choice.** `history._lock` only wraps the git commit itself, not the read-and-insert after it, so two concurrent writers' `history.commit()` calls can land in either order relative to each other's catch-up call. An earlier version fetched only `git log -1 HEAD`, which had two real bugs from that same gap: calling it again with nothing new re-ingested the unchanged HEAD (`history.commit()` no-ops are called unconditionally at every site — `watcher._reconcile` in particular, when a whole debounced batch turns out to be self-writes), duplicating a row per extra call; and if *two* commits landed before either caller's turn, only the newer was ever looked at — the older commit's row was silently **lost** until the next restart's backfill. A range has neither failure mode. `record_latest(db, post_ids=...)` additionally guarantees each caller's *own* ids are in its return value (a direct fallback lookup if a racing caller's catch-up already recorded them first) — the changes-log row is never at risk either way, only which caller's return value reports the `seq`.
- **`_catch_up`'s own read-then-insert needs a lock too, `changes._lock`** — a third bug in the same family, found only by live-testing genuine concurrent writers (5 parallel `POST /posts` produced 13 rows, several `(post_id, sha)` pairs duplicated 2-3x; no single-caller test caught it). The range fix above closes the *data-loss* failure mode of two commits racing ahead of a `-1` fetch; it does nothing about two callers both reading the same "last recorded sha" before either has inserted, both computing the identical range, and both redundantly re-ingesting it — a *duplicate*-row failure mode, not a lost-row one. `_lock` (module-level `asyncio.Lock`, the same pattern `vault.write_lock`/`history._lock` use for their own critical sections) wraps `_catch_up`'s entire body so the read and the insert are atomic with respect to every other caller. `tests/test_changes.py::test_concurrent_catch_up_calls_do_not_duplicate_rows` reproduces it deterministically via real `asyncio.gather` concurrency over independent connections (removing the lock makes it fail with 6x duplication, verified by hand).
- **`history.commits()` never takes a git pathspec, even though every caller only wants `.md` paths.** An earlier version supported a `-N` count bound for the (now-removed) "just the latest commit" fetch, and `-N` combined with a pathspec on a plain ref makes git skip non-matching commits and keep walking further back — `-1 -- '*.md'` on an attachment-only commit silently returned an *older* commit that did touch a `.md` file. `-N` is gone now that every caller uses a range (which has no such landmine), but the filtering stayed in Python (`changes._ingest`, one `.endswith(".md")` check) rather than reintroducing pathspec churn for a marginal cleanup.
- **A title rename produces both a `D` (old path) and an `A` (new path) for
  the same post in one commit** (`write_file`'s unlink-then-write, with
  `--no-renames` pinned so git never collapses them into one `R` status).
  `_ingest` dedupes to the non-`D` side per post per commit.
- **`changes.tags` is stored per row, not joined from `posts` at query
  time** — a deleted post has no `posts` row left to join against, and a
  tag-filtered SSE reconnect needs to filter *its* catch-up entry too.
- **`watcher._reconcile` and `cleanup._delete_expired` publish live SSE
  *before* their batch `history.commit()`** (unchanged by this feature — see
  their own comments), so those specific live frames go out with `seq=None`
  (no `id:`, same as pre-N-4). `record_latest` still runs after the commit
  either way, so a *reconnecting* client's catch-up query sees them —
  it's only the already-connected, live-delivery path for external
  edits/deletes and the TTL sweep that don't get a cursor id.
- **`rename_tag` gained its first-ever `events.publish` calls in this
  change** — before N-4 a retagged post never reached a live SSE client at
  all, not even without a cursor id. Found while wiring this up, fixed
  alongside it.
- **`changes.list_changes` 503s (`HistoryUnavailable`) when history is off**, same distinction `/posts/{id}/history` already draws — an empty list would look indistinguishable from "nothing has changed." A *separate* `HistoryUnavailable` from `service._common`'s: `changes.py` sits below `relay.service` (which already imports `changes`), so importing `service._common` back into it would be a real import cycle, not just a style mismatch.

## Vault lint (relay #198, N-5)

`relay/lint.py`'s `run(db)` — behind `GET /lint` and the `lint_vault` MCP tool — transcribes rules already in #0's prose, not new policy:

- `zero_tags` / `missing_domain_tag` / `missing_type_tag` — no tags at all, or missing one axis (not double-counted against each other)
- `stale_inbox` — a domain-tagged post still filed in `Inbox/` (`folders.py`'s move-on-first-tag invariant)
- `h1_missing` / `h1_title_mismatch` — no H1 in the body at all (a legacy post predating the convention) vs. an H1 present but no longer matching the title (classic cause: `frontmatter.sanitize_title` strips a rename character like `:` that the H1 still has). Compared with backticks stripped (a real H1 can legitimately style part of itself as code — the title side is implicitly backtick-free already) but *displayed* raw in `detail`, so the finding still shows the literal text
- `broken_link` / `link_to_deleted_post` / `broken_attachment_embed` / `wikilink_to_filename` — a `[[wikilink]]`/`#NNN` that doesn't resolve, resolves to a post `history.deletions()` says used to exist, an `![[embed]]` with a file extension that doesn't resolve to any existing attachment, or a *plain* `[[wikilink]]` whose target has that same file-extension shape (wrong syntax, not a missing post). All four carry `LintFinding.match` (the exact broken text) and report one finding per distinct `(rule, match)` pair per post — `LintFinding.occurrences` carries the real mention count, not one finding per mention
- `stale_last_updated` — a `hub`/`plan` post untouched for `STALE_HUB_PLAN_DAYS` (60)
- `zero_backlinks` — exempt: `digest`/`news`/`daily-digest`/`news-digest`/`briefing`/`financial-analyst`-tagged posts (dated snapshots nobody links back to). `link_to_deleted_post` reuses the same tag set: a link to a deleted post that carried one of these tags *at deletion time* (read from its last revision via `history.blob`) is suppressed rather than re-reported every run — a digest linking last week's already-rotated digests otherwise never stops being "broken"
- `empty_tag_config` — a `tags.yml` entry with zero live posts
- `zero_chunks` — embedded to zero chunks (reuses `vectors.unembedded_post_ids`); detail text distinguishes an empty body from a code-only one rather than asserting the code-fence cause unconditionally
- `master_doc_post_count` — #0's stated `<N> post` count vs. reality; silently skipped if #0 states none

**#0 is exempt from every rule above except the link checks** (`lint_this_post` in `run()`) — a root index reasonably breaks tag/folder/H1/staleness/embedding conventions, but a broken link there is a factual defect, not a convention. It's still walked for outbound links (posts it references get backlink credit either way), and `master_doc_post_count` still applies to it — that's about its own accuracy, not a convention.

**Link scanning and H1 *location* both dodge code, through two different helpers in `markdown_scan.py`** — a post *documenting* relay's own link syntax, or a fenced shell/TOML snippet containing `[[...]]`, used to get flagged for its own examples, and a heading-shaped line inside a fenced block used to count as a post's real H1. `links.extract_links` scans `strip_code`-ped content (fences *and* inline spans blanked); the H1 scanner locates its candidate line in `strip_fences`-ped content (fences only — inline spans left alone, since a real H1 can legitimately contain one and blanking it would corrupt the title comparison). `WIKILINK_RE` confines every capture group to a single line (no `\n`), so a stray unclosed `[[` in prose can no longer match all the way to an unrelated `]]` several paragraphs later. A bare `#N` below 10 or above `vault.read_id_counter()` (the id high-water mark) is excluded from the link rules entirely — footnote markers, procedure steps and GitHub issue/PR numbers collide with real ids far more at either extreme than a genuine cross-link does. `![[target]]` is only resolved as an attachment when `target` has a file extension (matching `main.js`'s own `HAS_EXT_RE` split); an extension-less embed is still a note-transclusion link to a post, like an ordinary wikilink. Findings are sorted by post id (`zero_backlinks` used to land grouped at the end purely by loop order). `main.js`'s `extractMedia` (feed-card thumbnail picker) and `edit-form.js`'s broken-link highlighter needed the equivalent JS-side fix — both now split on the same shared `CODE_SPAN_RE` (`util.js`) instead of scanning raw content; the highlighter also gained the embed exclusion (a valid `![[photo.png]]` was painting red, checked against post titles it was never going to match) and the single-line confinement.

Read-only, one pass over `posts` plus a handful of cheap follow-ups — safe to run on every lint check rather than a background job. A rule that needs a disabled feature (history for `link_to_deleted_post`, embeddings for `zero_chunks`) is skipped and named in `LintReport.skipped_rules` rather than the endpoint 503ing — a lint pass should degrade like `/status`, not fail outright over one unavailable rule.

## Authentication

Two channels checked by `require_api_key` (`relay/auth.py`): **Bearer `API_KEY`/`RELAY_API_KEYS`** (machine-to-machine) and **`relay_session` cookie** (web UI, signed `itsdangerous` token). **`identity.resolve_bearer()` is the only place a bearer is compared** (relay #198, B-7 — `auth.bearer_matches()` is now a thin `is not None` wrapper over it, kept for callers that only need a yes/no) — every surface (`/session`, `/events`, the MCP bearer gate, the OAuth verifier) traces back to it; it compares UTF-8 bytes per configured key because `compare_digest` on `str` raises on non-ASCII. Cookie-authenticated state-changing requests are rejected when `Sec-Fetch-Site`/`Origin` say cross-site (`auth.is_cross_site`), a second lock next to `SameSite=Strict`. The cookie is verified with a **live allowlist re-check on every request** — dropping a sub from `OIDC_ALLOWED_SUBS` revokes in-wild sessions immediately. No per-token revocation; a captured cookie stays valid until expiry.

**Per-agent identity** (relay #198, B-7): `require_api_key` returns an `identity.Actor` (`name`, `email`), not just a pass/fail — resolved from whichever configured key matched (`apikey` for the primary `API_KEY`, or a `RELAY_API_KEYS` name) or, for a cookie session, the OIDC user's email (falling back to `sub`). Every write route that needs provenance (`POST`/`PATCH`/`DELETE /posts*`, `POST /posts/{id}/edit|append|restore`, `POST`/`DELETE /attachments*`, `PATCH /tags/{tag}`) captures it as `actor: Actor = Depends(require_api_key)`, threaded into: the git commit's real `--author` field (`history.commit(..., author=...)`) — the committer stays the pinned `relay <relay@localhost>` identity regardless, so `git log --format='%an <%ae>'` shows who, `%cn <%ce>` still shows relay; the `changes` table's `author` column (read back off that same git author, not passed separately — `changes._ingest` maps the literal `relay` committer name to `NULL`, meaning "no specific actor"); and a post's `updated_by` front-matter field (set on create too, unlike `updated_at`, so a never-edited post still attributes to its creator — see the Storage section). A mechanical side-effect write that isn't really "by" whoever triggered it (a tag rename's bulk rewrite, an inbound-wikilink retarget on someone else's post) carries `updated_by` over unchanged rather than misattributing it; an external Obsidian edit round-trips whatever `updated_by` the file's own front-matter already had, same as every other field the watcher doesn't own. The MCP surface mirrors this via `_current_actor()` (`relay/mcp_server.py`), reading `fastmcp.server.dependencies.get_access_token()` — confirmed against fastmcp's own `AccessToken` construction, not assumed. Static bearer: `subject` is set by `_StaticBearerAuth` to the matched key's name. **MCP OAuth** (`verify_id_token=True`): fastmcp's `JWTVerifier.load_access_token` sets `subject = claims["sub"]` from PocketID's id_token and `claims` to that token's full decoded payload (so `email` — relay requests the `email` OIDC scope — is already a top-level claim there too, separately from `_RelayOIDCProxy._extract_upstream_claims`'s own copy nested under `claims["upstream_claims"]`, a different fastmcp mechanism). `_current_actor()` prefers `claims["email"]` over `subject` — PocketID's `sub` is an opaque IdP id, unreadable in a git author line or an `?author=` filter — mirroring `identity.actor_from_session`'s own email-first priority for the web UI's session cookie. **Per-key scopes are explicitly out of scope for this** — identity (who) and authorization (what they may do) are separate; scoping is relay #198's own documented fast-follow, likely via fastmcp's `AuthMiddleware` for the MCP surface.

**MCP OAuth** (`MCP_OAUTH_ENABLED`, relay #313): `relay/mcp_server.py`'s `_build_auth()` wires `MultiAuth(server=_RelayOIDCProxy(...), verifiers=[_StaticBearerAuth()])` — fastmcp's own OAuth 2.1 AS (`OIDCProxy`) brokering to PocketID, replacing an earlier hand-rolled implementation (`relay/mcp_oauth/`, deleted). `server` owns the OAuth routes/metadata and is tried first for token verification; `verifiers` are pure fallbacks with no routes of their own — the static `API_KEY` always works via `_StaticBearerAuth`, which delegates to `bearer_matches()` and reports `settings.mcp_scopes` (a plain `[]` here 403s "insufficient_scope" once `MultiAuth` enforces `required_scopes` against every verifier, not just the OAuth server — caught live, not by a test). Relay's own refresh tokens are hashed at rest (`RefreshTokenMetadata` — SHA-256, no raw token stored), and `client_storage` is `_oauth_client_storage()`: a **Fernet-encrypted** `FileTreeStore` (per-key JSON) at `<vault>/.relay/mcp_oauth/` (`settings.mcp_oauth_storage_dir`) — separate from `index.db`, pinned there instead of fastmcp's own default (`~/.fastmcp/oauth-proxy/`, outside the vault volume) so it rides the same Docker volume and durability guarantee. **Both the encryption and the non-`diskcache` backend are load-bearing and were Phase 5 audit findings** — read that function's docstring before changing either: passing `client_storage` at all opts out of the encryption `OIDCProxy` would otherwise apply, and the proxy persists the *upstream* PocketID access/refresh tokens, so without it live IdP credentials sit in cleartext in the vault tree (`.relay/` is excluded from Syncthing, so they do not replicate — but they are still long-lived cleartext IdP credentials beside the private notes, inside whatever backs that volume up). Setup unchanged: add `<RELAY_BASE_URL>/mcp/oauth/callback` to the PocketID client before enabling — `redirect_path` is pinned to that exact path (fastmcp's own default, `/auth/callback`, would collide with the web-UI's own callback route above).

**PocketID's own scope vocabulary is disjoint from relay's MCP scope, and `OIDCProxy` doesn't know that by default — found live against bespin's real PocketID, not by Phase 5's mock-IdP audit** (relay #313, 2026-09-18, the first real claude.ai connection after this branch first deployed). Two bugs, both invisible against a mock IdP that never enforced a real scope vocabulary:

- `_build_upstream_authorize_url` builds the upstream `/authorize` request's `scope` from `transaction["scopes"]` unconditionally (relay's own `["relay"]`, whatever the MCP client requested) and, by default (`forward_resource=True`), forwards the client's `resource` parameter too. PocketID's discovery document advertises `openid profile email groups offline_access` only, no RFC 8707 — it rejected outright with `invalid_request — The 'resource' or 'scope' parameter is invalid`. Fixed: `forward_resource=False` plus `extra_authorize_params={"scope": "openid profile email offline_access"}` in `_build_auth()` (`extra_authorize_params` is applied last via `dict.update()`, so it *overrides* rather than adds to `scope` — confirmed by reading `_build_upstream_authorize_url`). `_RelayOIDCProxy._prepare_scopes_for_token_exchange`/`_prepare_scopes_for_upstream_refresh` (fastmcp's own override hooks, unused before this) now return `[]` to omit `scope` on the token-exchange and refresh legs too, which would otherwise resend `["relay"]` and hit the same rejection there.
- Once that's fixed, PocketID echoes back the (corrected) scope it granted, and `OAuthProxy.exchange_authorization_code` takes an IdP-echoed `scope` as authoritative per RFC 6749 §5.1 — absent translation, that echoed string becomes the FastMCP JWT's own scope claim, so every `/mcp` call then failed `required_scopes=["relay"]` with `insufficient_scope`, immediately after a `200` token exchange. Fixed: `_RelayOIDCProxy._translate_scopes_from_idp` (fastmcp's documented hook for exactly this, the inverse of what `AzureProvider` does for its own prefixed scopes) substitutes `settings.mcp_scopes` unconditionally — PocketID's scope vocabulary was never meaningful for the downstream token.

`offline_access` in that overridden scope specifically because this proxy needs its own ability to silently refresh PocketID's token; unlike the web-UI login (`routes/auth.py`, `scope: "openid email profile"`), which re-authenticates via its own session cookie instead and never needed it.

**`verify_id_token=True` is the single most load-bearing argument in `_build_auth()`** — leaving it at its default makes `OIDCProxy` re-validate *PocketID's own access token* on every request against `required_scopes=["relay"]`, a scope no IdP will ever mint. The OAuth dance still completes and issues a token; every subsequent call then 401s. There is a regression test pinning it (`test_oidc_proxy_verifies_the_id_token_not_the_upstream_access_token`) because the failure is invisible until a real end-to-end login runs.

**The upstream id_token is re-verified on *every* `/mcp` request, and two Phase 5 findings live in that path.** `OAuthProxy.load_access_token` implements a token *swap*: it verifies relay's own JWT, then re-validates the stored upstream token via `_get_verification_token` — which, under `verify_id_token=True`, is PocketID's **id_token**. Two things in fastmcp disagree about that token's lifetime, and both bite:

- **The refresh trigger watched the wrong clock.** `load_access_token` decides whether to refresh from `upstream_token_set.expires_at` (the *access token's* `expires_in`) while validating the *id_token*. Whenever the id_token is the shorter-lived of the two, every request in the gap fails validation while `needs_refresh` is still False — no refresh is attempted and `/mcp` 401s on a completely healthy session. Reproduced live (3s id_token, 3600s access token): 200, then 401 six seconds later. `_RelayOIDCProxy._get_verification_token` now clamps `expires_at` down to the id_token's own `exp` so the trigger tracks what is actually validated, and `token_expiry_threshold_seconds=120` rotates ahead of expiry instead of during the outage. The clamp reads `exp` **unverified** on purpose — it can only ever move a refresh *earlier*, never extend a session, and the same token is fully verified moments later.
- **An IdP that omits `id_token` on refresh breaks `/mcp` outright — accepted risk, not fixed.** OIDC Core §12.2 makes `id_token` OPTIONAL on the refresh grant, and `exchange_refresh_token` *merges* the refresh response over the stored login response, so an IdP that omits one leaves the original login id_token in place to be re-validated forever. `_extract_upstream_claims` relaxes `exp` on the refresh path for exactly this reason (signature/`iss`/`aud`/`sub` still fully verified — the successful upstream refresh is the IdP's own live attestation, and the identity is only being read to re-run the allowlist), which fixes the refresh *grant*. It cannot fix the per-request path: `load_access_token` keeps re-verifying that same stale id_token and nothing can replace it, so `/mcp` 401s until the next interactive login. **Whether relay is affected depends on PocketID's behaviour, which was not confirmed during the audit** — if it is, `relay.mcp_server` logs a WARNING naming the cause exactly ("the IdP did not reissue an id_token on the refresh grant"). Verified end to end against a mock IdP in both modes.

**`exp={"essential": True}` in `_extract_upstream_claims` is load-bearing** — joserfc validates a claim only when it is *present*, so without it an id_token carrying no `exp` at all satisfies the registry and is accepted forever.

**PocketID's own refresh grant skipped re-authorization before 2.6.0** ([GHSA-w6p7-2fxx-4f44](https://github.com/pocket-id/pocket-id/security/advisories/GHSA-w6p7-2fxx-4f44)): a disabled account, a revoked client authorization, or a removed group membership did not stop a refresh from succeeding. Relay's own `OIDC_ALLOWED_SUBS`/`OIDC_ALLOWED_EMAILS` re-check runs on every refresh regardless, so relay-side revocation always works — but "the upstream refresh succeeded, therefore the session is still live" is only true on PocketID ≥ 2.6.0. Keep it current — confirmed **2.14.0** on bespin as of 2026-09-18.

**`OIDC_ALLOWED_SUBS`/`OIDC_ALLOWED_EMAILS` allowlisting isn't a stock `OIDCProxy` feature** — `_RelayOIDCProxy` overrides `_extract_upstream_claims` (fastmcp's documented hook for inspecting the upstream token response) to enforce it, independently re-verifying the id_token's signature against PocketID's own JWKS (`joserfc`, `iss`/`aud`/`exp`) rather than trusting the token response unverified. Runs on every refresh grant too, not just initial login (`_extract_upstream_claims` is called from both `exchange_authorization_code` and `exchange_refresh_token`), so dropping a sub from the allowlist revokes it at the next rotation — the same live-recheck property `auth.still_authorized()` gives the web-UI session cookie. `MCP_ALLOWED_REDIRECT_HOSTS` is translated into fastmcp's URI-pattern shape by `settings.mcp_allowed_client_redirect_uri_patterns` — confirmed fastmcp's own wildcard host matching (`redirect_validation._match_host`) uses the identical dot-boundary-suffix-with-apex-exclusion semantics this file's own docstrings require, so `*.mistral.ai` is exactly as safe as it always was; the property also explicitly adds `http://localhost:*`/`http://127.0.0.1:*` to every non-`None` pattern list, since fastmcp gives loopback URIs no automatic exemption once an explicit allowlist is supplied (unlike the old hand-rolled provider — a real regression caught and fixed before it shipped, not a hypothetical).

**Consent screen**: fastmcp's own (`require_authorization_consent=True`, the default — not `"remember"`), not a relay-owned page. Every single `authorize()` call generates a fresh transaction, a fresh consent screen, and a fresh signed binding cookie tied to *that* transaction (verified on the IdP return leg before any token exchange) — there is no persistent per-client approval state at all, so the confused-deputy bug class an earlier relay-owned consent gate needed a dedicated architectural fix for (approval briefly grantable from the consent page's own click, before that fix moved it to the post-login callback) has no equivalent surface here: there's no cross-request approval memory for a self-click to poison in the first place.

**Two known, accepted gaps** versus the deleted hand-rolled provider (relay #313 Phase 3, found by reading `fastmcp`'s source directly, not assumed): no RFC 6819 refresh-token-family revocation on reuse (`RefreshTokenMetadata` carries no parent/lineage field — replaying an already-rotated refresh token rejects that one token, but doesn't revoke any descendants an attacker raced ahead to obtain), and no deterministic local cascade from revoking a FastMCP-facing access token to its paired refresh token (RFC 7009 — `revoke_token()` only deletes local storage when the argument is itself a refresh token; for an access token it only attempts best-effort *upstream* revocation). Both are defense-in-depth downgrades, not baseline-OAuth violations — standard one-time-use rotation and short-lived access tokens still cover the common theft case — and were a deliberate trade-off for shedding ~820 lines of hand-rolled AS logic, not a silent loss.

## MCP

Two surfaces, **one tool definition**:
- **`relay/mcp_server.py`** — in-process, Streamable HTTP at `/mcp`. The only place tools are declared. Recommended.
- **`relay_mcp/server.py`** — stdio ↔ Streamable HTTP **bridge** for clients that can't speak remote MCP (e.g. Claude Desktop). It forwards every request to `<RELAY_BASE_URL>/mcp` and returns the server's result verbatim; tools, parameters and descriptions come from the server at call time, so nothing can drift. One fresh connection per request (`/mcp` is stateless), so a relay restart is invisible to the client. `tests/test_mcp_bridge.py` drives it end to end against a real uvicorn.

**The one bridge-only addition:** `add_attachment` gains a `path` parameter (a file on the client machine, uploaded through the presigned-slot REST flow). The in-process server must never gain `path` — that would be an arbitrary file-read on the relay host.

## Browser UI (`GET /ui`)

Single-page app on the REST API + SSE. ES modules, no build step — nothing is on `window`; imported bindings are read-only, so shared mutable state uses exported objects or private setters (`api.js` owns `apiKey` behind `setApiKey`/`clearApiKey`). `marked` and `DOMPurify` are **vendored** in `static/ui/vendor/` (not CDN-loaded) and `/` carries a CSP built by `main.ui_csp()`: `script-src 'self'` plus a hash of the one inline theme script in `index.html` — add another inline `<script>` and the hash list grows automatically, add an external script host and the CSP must be changed deliberately.

**Critical invariants:**

- **Colour lives in tokens only.** Every value declared in the two `:root` blocks of `app.css`; components use `var(--token)` or `color-mix()` from one. `tests/test_css_tokens.py` enforces this — fails on literals outside the blocks or a token declared in one theme but not the other.
- **Every theme clears a contrast floor** (`test_every_theme_clears_the_contrast_floor`): `--text` ≥ 10:1, `--body` ≥ 9.5:1 against `--surface`; `--on-accent` ≥ 4.5:1 against `--accent`. Faithful reproductions that can't hit the house target are named in `REPRODUCTIONS` with their measured value. Fix a shortfall by choosing a different palette member — never mix a new colour.
- **Catppuccin dark flavours have different accents by design**: Frappé=peach, Macchiato=blue, Mocha=mauve. Catppuccin Latte chips use `--text` (not an accent) — every Latte accent member falls under AA as chip text.
- **Mobile override block lives at the END of `app.css`.** A single-class override earlier in the file silently loses on source order. Check line numbers, not just specificity.
- **Draggable elements**: `animation-fill-mode: backwards` and no `to` keyframe. A `both` fill + explicit `to` outranks inline styles and swallows drag transforms.
- **Markdown content rules must go through `.post-body`** — a rule on `.pm-body` directly matches nothing (the rendered markdown is wrapped).
- **`min-width: 0` on every grid tile area.** A `1fr` track's automatic minimum is min-content; any non-shrinkable child overflows the card.
- **Six modals share chrome** (post, status, edit, history, shortcuts, lint). `test_every_desktop_modal_shares_the_same_chrome` asserts they agree as a set — change the look once. Both the keyboard-shortcuts and lint modals shipped after the other four and had to be added to `SHEETS` (`tests/ui/test_sheets.py`) by hand — the shortcuts modal was found in the exact "grab handle renders, `attachSheetDismiss` never wired" state that file's docstring warns about; sharing `.sm-inner` means a new modal is never at risk of *looking* different, just untested until it's added.
- **`apiSend` for DELETEs only** (no `Content-Type`, never throws on non-ok). Use `apiFetch` for anything that sends a body and needs to know if it worked.
- **Deleted post recovery lives in the status panel**, not the sidebar. It's a read over `history.git`, not a trash can.
- **Vault lint's UI is its own modal, not a status-panel drill-down** (`relay/static/ui/js/lint.js`, `#lintModal`). Status's "Vault lint" section runs the check on every panel open and headlines a count; "Browse issues →" opens `#lintModal`, which stacks over the status modal like `#historyModal` stacks over the post modal — closes on its own (Escape/×), added to `SHEETS` in `tests/ui/test_sheets.py`. Two-pane: findings list left, editor right. `.lm-inner` matches `.pm-inner`'s width (`94%`/`1320px`) so opening/closing a post from it doesn't resize the frame — deliberately not full-bleed, and not `.hm-inner`'s smaller cap either. `.lm-*` classes are distinct from `.hm-*` where a test asserts the latter bare/unscoped (`.hm-inner`); structural pieces scoped by parent id everywhere they're asserted (`.hm-rev`/`.hm-body-text` under `#hmBody`) were safe to reuse directly.
- **The lint pane hosts the real editor, not a preview.** `edit-form.js`'s `buildEditForm(container, post, {onSave, onCancel})` is shared by the standalone Edit modal and the lint pane — one implementation, one dirty-check, returned as `{isDirty}` for each caller's own close-time guard (`tryCloseEditModal` / `tryCloseLintModal`). `isDirty()` diffs every field (title/content/tags/source/expires) against its own starting value, not just content — the pane's main use is a tags-only fix. "Open post" (`.lm-open`) is a smaller, secondary action for what inline editing doesn't reach — Delete, History, backlinks.
- **Broken links are highlighted red in the editor, everywhere it appears** — a transparent-text `<pre class="ef-content-backdrop">` behind the textarea paints `.ef-broken-link`'s background where a `GET /links` fetch (cached in `edit-form.js`, invalidated on save) says a `[[wikilink]]`/`#id` doesn't resolve. Close to `relay.links`' definition, not main.js's richer render-time rules, but with two deliberate simplifications: an `![[embed]]` is skipped outright (this overlay has no attachment list to check it against, so painting every valid image/file embed red would be worse than not flagging embeds at all) and a bare `#N` still lights up regardless of the lint high-water-mark heuristic (a live "does this resolve" check, not a vault-wide-finding judgment). It does share the lint scanner's other exclusions: fenced/inline code spans (`CODE_SPAN_RE`, `util.js` — a post documenting its own link syntax must not paint its own examples) and single-line-only wikilink matching. Both layers must share every box-model property or the highlight misaligns. Selecting a link-rule finding also calls `scrollToMatch` on `LintFinding.match` (the exact broken text) to jump straight to it; other rules leave `match` `None`.
- **The post modal's "← previous post" breadcrumb doubles as "← Vault lint"** — opening a post from the lint pane sets `_externalOrigin`; `reopenLintModal` (not `openLintModal`) restores the same filter/selection on the way back rather than a fresh list.
- **History panel is fixed height** — panes built once, only contents swap. `min(82vh, 860px)`.
- **Header control order is a safety property**: `+ New Post` · theme · status · disconnect. Primary action and session-kill must not be adjacent. `test_header_controls_are_one_visual_set` pins this.
- **Use inline SVG, not glyphs or emoji** for icons. Colour emoji ignores CSS `color`; Unicode glyphs render unpredictably at small sizes.
- **iOS input zoom**: handled globally by `@media (hover: none) { input, textarea, select { font-size: 16px !important } }` — not per-form.
- **CSP forbids inline event handlers and `javascript:` URLs** (`script-src` has no `'unsafe-inline'`). Wire handlers with `addEventListener`; `style=` attributes are fine (`style-src` allows inline).

## Tags · master doc · TTL

- **Tags:** front-matter list; stored with sentinel commas (`,news,ai,`) for `LIKE '%,tag,%'` matching. Per-tag TTL in `<vault>/.relay/tags.yml`; `set_tag_config` with neither field removes the entry (it is the only way to drop a tag from `list_tags` once its posts are gone).
- **Search:** SQLite FTS5 over title/content/source/tags — porter-stemmed, bm25-ranked. Falls back to `LIKE` if FTS5 unavailable.
- **Master doc (`id=0`):** `Master Document.md` at vault root, seeded at startup, `DELETE` blocked, TTL-exempt. Update via `update_post(id=0, …)`.
- **TTL:** off by default. Precedence: per-post `expires_at` > per-tag > global. Shortest TTL wins for multi-tag posts. **`expires_at` is validated and normalised to `YYYY-MM-DDTHH:MM:SSZ`** (`models.normalize_expires_at`) because the sweep compares it *lexically* in SQL — `"1 week"` sorted below every real date and got swept. The sweep also only compares values in that shape (`GLOB` guard) and warns on anything else in hand-edited front-matter.
- **Dot-directories are never vault content.** `vault.is_hidden_path` excludes `.relay`, `.obsidian`, `.trash` (Obsidian's own trash keeps the note's `id` — indexing it resurrected deletes), `.stversions`… from the startup scan, the watcher and the `assets/` scan.
- **The watcher re-stamps a duplicate.** An external file carrying an id already indexed at a *different, still-existing* path (Obsidian "Duplicate note") gets a fresh id, like `rebuild_index` does — upserting it used to repoint the id at the copy. A rename (old path gone) is not a collision.
- **`database.connect()` is the only way to open the index** outside `init_db`: Row factory, `busy_timeout`, sqlite-vec extension. Six ad-hoc copies used to disagree on which of those they set.

## Semantic search (proof of concept, relay #253)

`RELAY_EMBEDDING_ENABLED` (off by default everywhere, including production). Adds `mode=keyword|semantic|hybrid` to `GET /posts` and `list_posts` (both MCP surfaces), and a ranking-mode select in the browser UI search bar (hidden unless `features.search.embeddings` in `/status` is true). `mode=semantic|hybrid` 503s if unavailable. Can be combined with `tag`/`folder` (v1.5.0) — see the Issue 4 bullet below.

- **Chunking** (`chunking.py`): H2/H3-aware, runt-merge, giant-split with overlap. **Embedding cache** (`vectors.py`): content-addressed by `(model_id, chunk_body)` hash — unchanged content is a cache hit, never re-embedded, and the cache survives restarts (no cascade from `posts`).
- **`.relay/models`** — fastembed's downloaded ONNX model. **`.relay/hf-home`** — `huggingface_hub`'s cache root (xet fast-transfer disabled via `HF_HUB_DISABLE_XET=1`; its own cache/log path ignores `cache_dir` entirely and is derived from `HF_HOME` at import time, so both are set at `embedding.py` module load, before fastembed can be imported anywhere). Both under `.relay/` so they ride the vault volume in Docker and survive container restarts instead of re-downloading.
- **Startup never blocks on embedding.** `rebuild_index`'s bulk pass runs with `index_upsert(..., sync_embeddings=False)` — SQL-only, fast, safe to run inline in the ASGI lifespan. `vault.backfill_embeddings` (the deferred work) runs as a background `asyncio.create_task` from `main.py`'s lifespan, same pattern as `cleanup_loop`, logging `Embedding backfill starting` → periodic `N/M posts checked` (15s cadence) → `Embedding backfill complete`. **This split exists because of a real production outage**: embedding every post inline at startup blocked the ASGI server from accepting *any* connection — including `/health` — until the whole backlog finished; on a real vault that's minutes of total downtime on every restart. Never reintroduce an inline bulk-embed call.
- **Memory footprint — root cause found and fixed.** `EMBEDDING_THREADS` (v1.1.2) measured no improvement in production — turned out to be the wrong theory: constructing `FastEmbedBackend` costs ~570MB of RSS by itself (onnxruntime session + model weights, measured locally: ~67MB → ~637MB before a single embed call), and that cost is flat across usage afterward, not per-call or per-thread. `embedding.unload_if_idle()` (polled every 60s from a background task in `main.py`'s lifespan) now drops the backend after `EMBEDDING_IDLE_UNLOAD_SECONDS` (default 300) of no activity — trading a several-second reload on the next embed call for the memory back. `gc.collect()` alone only reclaimed ~200MB of that ~570MB in testing (the rest sits in glibc's malloc arenas, not leaked, just not returned to the OS); `ctypes.CDLL("libc.so.6").malloc_trim(0)` after the `gc.collect()` is what actually returns it — verified end-to-end: 621MB → 105MB after unload, ~640MB again after reload. `malloc_trim` is best-effort (wrapped in a broad except) for platforms without glibc.
- **`vectors.sync_post_chunks` never raises and never commits.** Embeddings are derived data: a backend that cannot load (download blocked, OOM) used to propagate out of the write path, roll back the create and 500 every update — a read-only vault while embeddings were on. It now logs and moves on (the backfill catches up, and skips a failing post instead of aborting). Commits belong to the caller: `create_post`'s `BEGIN IMMEDIATE` and `update_post`'s multi-statement write were being committed from inside the helper. `rebuild_index` prunes chunks whose post is gone (`vectors.prune_orphan_chunks`).
- **A ranked query degrades, a disabled feature errors.** `mode=semantic|hybrid` with embeddings *configured off* is a 503 (deliberate — a caller asked for something this relay doesn't have). If the feature is on but the backend fails *at query time*, `_list_posts_ranked` answers keyword-ranked with `search_timing.degraded=true` instead of a 500.
- **SSE queues are bounded** (`events.QUEUE_MAXSIZE`): a subscriber that stops reading gets its oldest event dropped and an `OVERFLOW` marker; the generator closes the stream and the client reconnects with `Last-Event-ID`.
- **Idle-unload's corollary (v1.1.4): the write path needed the same `asyncio.to_thread` treatment as search.** `vectors.sync_post_chunks` (`create_post`/`update_post` → `index_upsert`/`index_insert`) called `get_backend()`/`embed_documents()` directly on the event loop — harmless before idle-unload (the backend loaded once per process lifetime), a real stall risk after it (a cold reload can now happen on any edit, not just the first ever). Both calls now go through `asyncio.to_thread`, same as `semantic_search`'s `_embed_query`. **Any future call site that touches `embedding.get_backend()` needs this too** — it's no longer safe to assume the backend is already warm.
- **The embedding dimension is derived from `EMBEDDING_MODEL`, not hardcoded.** `embedding.resolve_dim(model_id)` looks up a model's dimension from fastembed's static registry (`TextEmbedding.list_supported_models()` — pure in-memory metadata, no download, safe to call in tests/CI). `vectors.init_vec` compares that against `embedding_state` (a one-row table recording the dimension the on-disk `vec_chunks` table — a vec0 virtual table, whose column width has no `ALTER` — was actually built at) every startup; a mismatch means the configured model's dimension changed since the schema was created, so `vec_chunks` is dropped and recreated at the new width and `chunks` is cleared. No explicit re-embed step is needed after that: the embedding cache is already keyed on `(model_id, chunk_body)` (see `_hash`), so *any* `EMBEDDING_MODEL` change — same dimension or not — already makes every existing chunk a cache miss on its own; the always-runs-at-startup `vault.backfill_embeddings` background task just re-fills whatever's empty. The check only runs while `embedding_enabled=true` — toggling the flag off leaves an existing table alone rather than comparing it against the disabled-state placeholder dimension, which would otherwise misfire a rebuild on every disable/re-enable cycle. Bigger multilingual models fastembed offers today: `paraphrase-multilingual-mpnet-base-v2` (768d, 1.0GB), `multilingual-e5-large` (1024d, 2.24GB) — both a pure `.env` change now.
- **`/status`'s `embeddings` field (v1.2.1) is the diagnostic surface for all of the above** — `status.embedding_status()` reports `enabled`/`available`, the configured `model` + resolved `dimension` + `model_size_mb` (via `embedding.resolve_dim`/`resolve_size_mb`), `backend_loaded` (`embedding.is_loaded()` — is the ~570MB model actually resident right now, or idle-unloaded), `idle_unload_seconds`/`threads` (the configured knobs), coverage counts (`posts_total`/`posts_embedded`/`posts_missing`/`posts_missing_ids`/`chunks_total`/`cache_entries`, from `vectors.coverage`), and `backfill` (`vault.backfill_status()` — `running`/`checked`/`total`/`started_at`/`completed_at` for the current or most recent backfill run). Built to answer, without a shell or a log tail, the exact questions the v1.1.1-v1.1.3 production incidents raised live: is it actually enabled, which model, is it still crunching, and how much is left.
- **Runtime control (v1.3.0): `PATCH /embeddings` and `POST /embeddings/backfill`** (plus `set_embeddings_enabled`/`trigger_embedding_backfill` on both MCP surfaces) — pause/resume and re-trigger the backfill without a restart. Both live in `status.py` (`set_embeddings_enabled`, `trigger_backfill`) alongside `embedding_status`, sharing its `EmbeddingStatus` response shape. Design constraints worth knowing before touching this again:
  - **The toggle mutates `settings.embedding_enabled` directly, in memory only.** Every embedding call site already re-checks that setting per call rather than caching it (this was already true before v1.3.0), so the effect is immediate with no new state variable; a restart reverts to whatever `.env` says, same as any other setting. Deliberately not persisted — a second source of truth alongside the env var was judged not worth it for what's meant to be an operational pause/resume, not a permanent config change.
  - **Enabling can only resume against the model/dimension the schema was already built for.** `vectors.current_schema_dim` (mirrors `init_vec`'s own fallback: `embedding_state` row if present, else the disabled-state default) is compared against `embedding.resolve_dim(settings.embedding_model)`; a mismatch 409s asking for a restart rather than attempting a live schema rebuild — that migration only runs in `init_vec` at startup, and doing it under in-flight reads is out of scope.
  - **Disabling force-unloads immediately** (`embedding.force_unload()`, unconditional — refactored out of `unload_if_idle` as a shared `_do_unload()`) rather than waiting for `EMBEDDING_IDLE_UNLOAD_SECONDS`: an explicit "off" means the memory is wanted back now.
  - **Enabling auto-triggers a backfill** (`vault.spawn_backfill()`) so newly-covered posts don't wait for the next restart — same function `POST /embeddings/backfill` calls directly, and what `main.py`'s lifespan now calls too (refactored out of the old inline `_embedding_backfill`).
  - **`POST /embeddings/backfill?force=true` wipes `chunks`/`vec_chunks`/`embeddings_cache`** (`vectors.reset`, synchronous, before the response returns) rather than relying on the content-addressed cache — for when the cache itself, not just its completeness, is in question. A plain re-trigger without `force` is deliberately a fast no-op in steady state.
  - **A second run can't be triggered while one is in flight** — `vault.backfill_status()["running"]` is checked before starting another; racing two on `vault._backfill_state`'s shared counters would produce nonsense. `vault.spawn_backfill()` marks `running` *synchronously* before scheduling the task (so an immediate `/status` poll doesn't race the task's first event-loop turn), and a `add_done_callback` clears it if the task is cancelled before ever running — a task cancelled before its first step never executes even a `finally`, which a fast shutdown could otherwise leave stuck reporting a phantom backfill forever.
- **`posts_missing_ids` (v1.5.0)** — a live vault usage report on relay #253 found `posts_missing: 1` with no way to learn *which* post, or why. `vectors.unembedded_post_ids` (`posts` minus `DISTINCT post_id` in `chunks`, capped at 50) closes that. There's exactly one root cause worth naming, not a per-post reason to compute: every write path awaits `sync_post_chunks` inline and `backfill_embeddings`'s loop has no per-post try/except, so the only way a post has zero chunks is `chunking.chunk_post` genuinely returning `[]` for it — in practice, a body that's entirely a fenced code block, stripped before chunking ever sees it (confirmed against a real vault: the one missing post there was exactly this — a single `rclone` command in a code fence, nothing else).
- **Ranked modes now accept `tag`/`folder` (v1.5.0), fixing the usage report's Issue 4.** `vectors.semantic_search` and `service._keyword_ranked_ids` each grew the same `tag`/`folder` params the unranked path already had, using the identical condition shape (`posts.tags LIKE '%,tag,%'` / `posts.path LIKE 'folder/%'`) so a filtered `hybrid` query fuses two lists that agree on eligibility. `vec_chunks` has no partition/metadata columns, so sqlite-vec can't push the filter into the KNN index itself — `semantic_search` applies it as an ordinary join *after* the k-nearest chunks are pulled, and widens k to the full chunk count whenever a filter is present so filtering can't starve a small fixed k into returning nothing. Full-corpus KNN per filtered query is fine at this vault's scale (hundreds of chunks) but is a real, unbounded-with-vault-size cost — revisit before this filters a much larger vault. `RankedSearchFilterUnsupported` (the old 400) is gone; REST/MCP docs updated to match.
- **`search_timing` on ranked responses (v1.5.0), fixing the usage report's Issue 5.** `PostListResponse`/`PostSummaryListResponse` gained an optional `search_timing: {cold_start, embedding_ms}`, populated only by `_list_posts_ranked` (`mode="semantic"`/`"hybrid"`; absent on plain keyword search, which never touches the embedding backend). `cold_start` is sampled from `embedding.is_loaded()` *before* calling `vectors.semantic_search` — the model is unconditionally loaded by the time that call returns, so "was it cold" only has a signal if read first. Lets a caller tell a genuinely slow vault from a session's first query paying the idle-unload reload cost, without a log tail.
- **Digest/news posts are excluded from embedding entirely (relay #198, O-4).** `folders.DISPOSABLE_TAGS` (`digest`/`news`/`daily-digest`/`news-digest`/`briefing`/`financial-analyst` — the exact set `lint.py`'s `zero_backlinks`/`link_to_deleted_post` already treated as "dated, disposable snapshot", now one shared constant instead of two copies) short-circuits `vectors._sync_post_chunks`: a post carrying any of these tags is never chunked or embedded, and any chunks it already had (from before a retag) are dropped. Months of near-identical briefings were otherwise dominating similarity ranking far more than they'd ever usefully match against. `vectors.unembedded_post_ids` and the new `vectors.excluded_post_count` both filter/count by the same tag set — `/status`'s `posts_excluded` field reports the count, and `posts_missing` is `posts_total - posts_embedded - posts_excluded` so a deliberate exclusion doesn't misreport as a diagnosable failure. `lint_vault`'s `zero_chunks` reuses `unembedded_post_ids` directly, so it stopped flagging every digest for free — no separate lint change needed.
- **Advisory duplicate-guard + related posts (relay #198, N-7).** `vectors.find_similar_posts(db, exclude_post_id=, title=, content=)` is the one shared lookup behind both surfaces: it runs `semantic_search` with `f"{title}\n\n{content}"` as the query and drops `exclude_post_id` from the results (self-similarity would otherwise always be the top hit at distance 0). **Never raises** — a query-time backend failure is logged and swallowed to `[]`, same guarantee `sync_post_chunks` already makes on the write side, because this is pure advisory enrichment riding along an otherwise-successful publish or read, not a caller who explicitly asked for ranked results and needs to know they degraded (contrast `_list_posts_ranked`'s `search_timing.degraded`). `vectors.similarity_score(distance)` converts L2 distance to cosine similarity (`1 − d²/2`) for a friendlier `score` field.
  - **`POST /posts`/`publish_post` gains `similar: [{id, title, score}]`.** Computed *after* the write, its history commit, and its SSE publish — deliberately outside `vault.write_lock`, since a read-only similarity lookup has no business extending how long a write holds the lock, and it must never fail or slow down the create it rides along with.
  - **`GET /posts/{id}/related`/`get_related`** answers "similar but not already linked" — an automatic to-do list of missing `[[wikilinks]]`, not a general "more like this": a candidate already reachable via an outbound or inbound `[[title]]`/`#id` link (computed the same way `get_backlinks` does) is filtered out, since that relationship is already explicit. Unlike the advisory guard above, this one **does** error loud (`SemanticSearchUnavailable` → 503) when embeddings aren't enabled — a caller asking for this specific feature should see "not available", not an indistinguishable empty list, same distinction `mode=semantic` search already draws.
  - **`_SIMILAR_DISTANCE_THRESHOLD` (0.9) is provisional**, unlike the golden-set-swept `_CONFIDENT_DISTANCE` (1.1) used elsewhere in this file — there's no labeled duplicate-pairs dataset to tune against yet. Picked conservatively tight because a false positive here just costs a human a glance at an unrelated suggestion, not a wrong search result. Revisit once real usage shows whether it's too tight or too loose.

## Exporting a vault

```bash
uv run python scripts/export_vault.py --source https://your-relay.example.com --vault ./snapshot
```

Pulls every post over REST and builds an index — output is a vault relay can serve as-is. Standalone script with no test coverage; re-run manually after changing `vault.write_file`. Caveats: per-tag TTL config isn't exported; `--vault` must be empty.
